## 1. Постановка задачи и исходный сценарий
Необходимо разработать консольное приложение для ОС Linux, моделирующее работу магазина с двумя отделами с непересекающимся ассортиментом. Покупатели получают списки товаров и приобретают их в строгом порядке, перемещаясь между отделами и становясь в очереди. Продавцы обслуживают клиентов по одному и засыпают при отсутствии людей в очереди. Требуется реализовать последовательную имитационную программу, отражающую все события в терминах предметной области.

## 2. Архитектура моделирования
Модель реализована как дискретная последовательная симуляция, управляемая глобальным циклом (event loop). Сущности предметной области отображены на структуры данных `Customer` и `Department`.
Во избежание состояний гонки (race conditions), таких как ложное засыпание продавца в момент перехода покупателя, итерация главного цикла строго разделена на три фазы:
1.  **Освобождение:** Продавцы декрементируют таймер `service_time_left`. При достижении нуля покупатель получает товар, а продавец освобождается.
2.  **Перемещение:** Покупатели анализируют свой список (`shopping_list`), находят нужный отдел и встают в его очередь (изменяя состояние на `STATE_QUEUEING`).
3.  **Загрузка/Сон:** Свободные продавцы извлекают клиентов из очереди (`dequeue`) и запускают таймер обслуживания. Если очередь пуста, продавец переходит в состояние сна (`is_sleeping = true`).

## 3. Пользовательский интерфейс и Ввод/Вывод
Интерфейс представляет собой консольное приложение (CLI).
*   **Системные вызовы:** Для вывода событий на экран используются низкоуровневые системные вызовы `write` с дескриптором `STDOUT_FILENO`.
*   **Логирование:** Для выполнения дополнительных требований реализовано дублирование вывода в файл `sim_log.txt` через файловый дескриптор, полученный вызовом `open`.
*   **Интерактивность:** Между итерациями (тактами) цикла внедрена задержка через системный вызов `usleep` для наглядного отображения процесса.
*   **Инициализация:** Входные параметры (ассортимент, списки покупок, время обслуживания, продолжительность дня) считываются из конфигурационного файла `config.txt`.

## 4. Запуск и завершение программы
*   **Запуск:** Программа компилируется с помощью `gcc` и запускается из командной оболочки `bash`. В качестве аргумента командной строки можно передать путь к конфигурационному файлу (по умолчанию ищется `config.txt`): `./shop_sim config.txt`.
*   **Завершение:** В программе реализован параметр продолжительности рабочего дня. По истечении заданного количества тактов магазин закрывает двери. Программа корректно завершается штатным образом (выход из главного цикла), когда счетчик `active_customers` достигает нуля — то есть когда все вошедшие до закрытия покупатели завершили свои списки.

## 5. Критическая оценка применения ИИ
В ходе выполнения работы использовался ИИ-ассистент (Google Gemini) для анализа базового каркаса конечных автоматов, настройки системных вызовов, выявления недостатков программы, рекомендаций по внесению необходимых правок, а также генерации тестовых конфигураций, скрипта тестирования и примера отчёта по заданию, который я отредактировал.
*   **Оценка:** ИИ успешно справился с оценкой неточностей моего кода, дал рекомендации о том какие правки необходимо внести так как моя первоначальная реализация логики содержала архитектурные изъяны: мгновенное обслуживание (отсутствие таймера) и смешивание логики покупателей и продавцов в одной фазе, что приводило к логическим ошибкам (ложные сообщения о засыпании/пробуждении). Кроме того, ИИ помог мне с написанием тестовых конфигураций, скрипта тестирования и с составлением примера отчёта по заданию.
*   **Ручные правки:** Код был подвергнут существенному рефакторингу. Был внедрен трехфазный такт симуляции, добавлено чтение всех массивов из файла конфигурации с динамическим выделением памяти (`malloc`/`free`), а также реализован таймер обслуживания для продавцов и ограничение рабочего дня.
